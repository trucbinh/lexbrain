# Specification-First Records

OpenSpec is the only requirements and change-planning source. Do not create a second specification, task list, or capability description here. Every record must reference the relevant `openspec/changes/<change>/` artifacts and may summarize review findings or execution results without copying the requirement text.

Use these paths as needed:

- `reviews/<change>.md`: independent reviewer, reviewed artifact paths, evidence-backed verdict, findings, and cuts.
- `runs/<change>.md`: user approval recorded only after the user's explicit message; worktree/branch; implementation progress references; validation commands and results; verification and delivery readiness.
- `decisions/<change>.md`: non-obvious implementation choices, alternatives, rationale, evidence, and impact.

The reviewer runs in a separate fresh VS Code chat with the read-only `Spec First Reviewer` agent. The coordinating agent may preserve the review response under `reviews/`; it must not alter the verdict. User approval applies only to the named change and the exact reviewed artifacts. A requirements or design change requires another review and approval.

OpenSpec's default `core` profile is retained to avoid changing the user's global OpenSpec workflow settings. Use the repository-scoped `/spec-first-verify` prompt for requirement-to-implementation verification together with `openspec validate`. OpenSpec's native `/opsx-verify` is not generated by the core profile.

Windows supports Git worktrees, but the upstream spec-first commit gate is POSIX-only. Use a manually inspected Git worktree for implementation; do not install a commit hook. Do not commit, push, create a PR, or archive without a separate user instruction. Archive only after verification and all applicable project gates pass.
